# 0.5.8 并发与原文保真候选验证记录（2026-09-01）

## 用途、输入和输出

本文件记录公开仓库建立前对 `0.5.8` 源码候选的阻断问题复现、修复和验证。输入是 `0.5.7` 源码、两轮发布前独立代码审查、并发探针和 Markdown 往返样例；输出是项目级不可变状态转换、同正文幂等规则、状态证明完整性、存储层项目目录硬校验、未编辑原文保真、回归测试和当前证据边界。

依赖 Node.js 22 或更高版本、npm 和支持原子硬链接及重命名的本地文件系统。限制是本记录没有把 `0.5.8` 安装进真实 Codex 宿主，也没有测试网络文件系统、第二台设备或跨机器并发。

## 发布前失败证据

### 同基准并发覆盖

两个独立 Node 进程从同一个权威版本同时调用更新。修复前，新增回归测试第一轮就出现两个调用都返回成功；独立审查的 50 轮探针中有 46 轮双成功，最终权威指针只保留一个正文，并出现两个相同修订序号。这证明旧实现会静默丢失一次更新，不是理论风险。

第一次修复尝试采用 `proper-lockfile@4.1.2`。其过期锁恢复仍是先读取固定锁状态、再删除固定路径并重建；多个恢复者可能在检查和删除之间互相穿越。固定 10 次聚焦窗口在第 4 次失败，Windows 返回两个进程并发替换 `current.json` 的 `EPERM`。该依赖因此移除，相关绿色结果作废，没有写成最终修复证据。

不可变转换的第一版在单个完整套件下通过，但第二轮独立复审把 6 个完整套件并行运行时得到 `0/6`：每次都在“8 个相同正文请求应全部幂等成功”处失败，单轮只有 1 至 7 个调用报告成功。根因是请求读到旧状态后，另一个进程已经提交相同正文；迟到进程仅凭“修订已提交”标记把目标复制成 `rev-restore-*`，入口的旧基准预检还可能在进入幂等判定前直接拒绝。这个失败说明原先的 `65/65` 和 `650/650` 不能证明后续候选，相关结果已经作废。

同一轮复审还确定性复现了两个问题：`A -> B -> 恢复 A` 后原样重试会返回版本冲突并可能重复生成恢复版本；修改 `current.json` 的 `committedAt` 后，读取接口会返回伪造时间。状态证明文件的提交时间或父状态被改写时也没有立即报错。

### 非目标原文变化

修复前，`# 标题\r\n\r\n正文\r\n` 经过画布模型后全部变成 `LF` 行尾；合法的无外框 Markdown 表格也被整体改成带外框和空格的格式。对应两个逐字断言都稳定失败，说明“只改一个单元格”会让未编辑内容发生变化。

## 修复边界和数据流

- `.codex-text-control/authority-anchor.json` 保存不可变状态起点；`transitions/` 为每个状态保存至多一个不可变后继转换。
- 同一状态的转换文件通过排他硬链接发布。多个进程从同一基准竞争时，只有一个能创建目标文件；其余进程重新沿链读取后返回版本变化错误。
- `current.json` 是可重建的链上检查点。状态编号、修订编号、提交时间和父状态必须与不可变证明全部匹配；检查点缺失或不匹配时从锚点恢复，旧检查点仍会沿转换链追到最新。
- 已提交、对历史可见和正文内容索引分别使用不可变标记；失败候选可以留作内部恢复材料，但不会出现在用户版本历史，也不会被误标成历史恢复。
- 相同正文使用 SHA-256（安全哈希算法 256 位）内容指纹复用已有修订。请求发现权威正文已经等于目标正文时直接返回当前版本；看到已提交标记后先重读链尖端，只有状态仍未变化才按历史恢复处理。
- 历史恢复复制旧快照为新的修订编号，恢复后可以继续更新而不会形成版本循环；相同恢复请求原样重试或恢复后再次保存未变化正文时复用当前恢复版本。
- 存储层直接拒绝空项目目录，不再保留 `process.cwd()` 回退。
- 画布块保存每一行原始行尾；表格保存原始行和原始单元格，序列化时逐字复用未编辑行，只重建被修改的表格行。
- 保留旧修订 JSON 和 `current.json` 读取兼容；新增锚点与转换目录。`0.5.7` 不理解新转换链，因此回退只能诊断，不能继续提交。

## 自动化与性能结果

- 最终完整自动测试：`74/74` 通过；其中存储聚焦套件 `26/26` 通过。
- 同一最终候选完整套件连续 10 次：共 `740/740` 项通过，失败运行 `0`，当前冻结重复窗口内观察到的不稳定率为 `0/10`。
- 修复前 6 个并行完整套件为 `0/6`；最终候选按相同压力形状为 `6/6`，共 `444/444` 项通过。该压力结果专门覆盖已知交错，不替代顺序稳定性窗口。
- 高风险聚焦窗口连续 10 次通过；每次覆盖 6 轮双进程同基准更新、12 轮每轮 8 进程竞争、旧指针延迟写回和历史恢复后继续编辑。
- 旧版 `write.lock` 遗留时，新状态转换不等待、不删除该锁，仍保持每个基准最多一个更新成功。
- 原文保真：未编辑 `CRLF` 正文逐字还原；修改一个表格单元格时，未编辑表头、分隔行和行尾逐字不变。
- Node.js 内置覆盖率在当前生产侧得到行覆盖 `96.23%`、分支覆盖 `79.10%`、函数覆盖 `88.54%`。该数字不包含通过 `vm` 执行的界面脚本，属于内部结构覆盖，不能当成真实宿主或外部能力成绩。
- 600 个不同的 1 KB 正文顺序提交三轮，耗时分别为 `5752.06`、`5805.79`、`5831.34` 毫秒，中位数 `5805.79` 毫秒。该探针只报告当前 Windows、本地磁盘和固定负载下的观测范围，不能单独证明规模增长曲线，也不是跨机器性能承诺。
- npm 官方注册表当前报告生产依赖已知漏洞 `0`；`96` 个包签名和 `11` 个来源证明通过。已知漏洞和签名检查不能证明没有未知供应链风险。
- 从当前已提交候选创建全新本地 Git 克隆，不复制原目录的 `node_modules`；`npm ci --ignore-scripts` 安装 `96` 个包后，完整 `74/74`、语法检查和 MCP 探针通过，克隆工作树保持干净。该结果证明本机干净克隆可复现，不等于第二位用户或其他操作系统独立复现。

## 已证实、未证实、失败与限制

### 已证实

- 已复现并修复同目录多进程静默丢失更新。
- 已证明旧指针延迟写回不会回退权威内容，历史版本恢复后仍可继续编辑。
- 相同正文的迟到并发请求和历史恢复原样重试会幂等返回当前权威修订，不再重复生成恢复版本。
- 检查点提交时间被改写时会从权威链恢复真实值；状态证明的时间或父状态不一致时明确拒绝读取。
- 缺少项目目录会在 MCP 协议层和存储层同时失败。
- 画布不会仅因解析和序列化就改写未编辑行的行尾或表格排版。
- `0.5.7` 的修订和指针数据无需迁移即可由 `0.5.8` 读取。

### 未证实

- `0.5.8+codex.20260901204256` 尚未安装进真实 Codex 并完成点击闭环。
- 没有网络文件系统、跨机器分布式锁、macOS 或 Linux 真实宿主结果。
- 没有公开持续集成运行、陌生用户独立安装或公开发行版证据；当前只有本机全新克隆结果。
- 当前缺少适用于 Codex 上下文画布的外部权威能力基准，不能声称领先同类项目。

### 失败与限制

- 修复前的并发和原文保真测试均为阻断失败，旧实现不能按公开候选口径继续上传。
- 第一版不可变转换在低负载下的绿色结果也已被并行 `0/6` 推翻；失败原因、修复和复验均保留在本记录中，不能继续引用旧 `650/650` 作为最终候选证据。
- 状态转换依赖本地文件系统的原子硬链接和重命名语义，不等于数据库事务或跨机器一致性协议。
- 网络文件系统、不支持硬链接的文件系统和混用 `0.5.7`/`0.5.8` 两个写入进程没有验证；这些环境不能继承当前结论。

## 回退

若 `0.5.8` 后续真实宿主复验失败，可先备份 `.codex-text-control/`，再重新安装 `0.5.7+codex.20260901154437` 做只读诊断。0.5.7 能看到旧修订文件，但不理解新增状态转换链；回退后不得继续提交，恢复写入前应重新升级到 0.5.8。

客观结论：`0.5.8` 已通过当前机器上的自动化、顺序重复稳定性、冻结并发压力、状态证明完整性、跨进程更新和未编辑原文保真检查，可以称为“源码候选版”；在真实 Codex 复验、公开持续集成和陌生用户独立复现完成前，不能称为可发布或生产可用。
