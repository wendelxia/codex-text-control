# GitHub 同类项目证据对比（2026-08-31）

> 这是 `0.3.0` 阶段的历史快照，表内测试数和真实宿主状态不代表当前版本。当前状态以 [`0.5.7` 验证记录](verification-0.5.7-2026-09-01.md) 为准；本文件保留原始数字，用于追溯当时为什么坚持窄定位。

## 方法和边界

本对比只针对与“提示词或上下文编辑、版本和恢复”直接相关的公开仓库。Stars（星标）和提交数来自 2026-08-31 的 GitHub 页面快照，会随时间变化；功能结论同时检查 README 和本地浅克隆代码。浅克隆的本地提交数只有 1，不能代替网页完整历史，因此不拿它做负面结论。

这个领域没有一套公认、可直接衡量“上下文编辑器工程质量”的权威基准。下表是公开、可复现的工程检查，不是权威排行榜，也不能声称领先整个行业。

## 我们真正值得做的窄定位

“Codex 专用的权威上下文确认插件”：模型只能提出或打开，用户才能保存和提交；提交后既有磁盘版本，也有当前对话里的新用户消息。这个闭环与通用提示词仓库并不相同，可以成为一个清楚的小切口。

不应扩成另一个 Langfuse。版本 diff 可复用成熟文本差异算法，通用评测可接 promptfoo，运行可观测性可接 Langfuse；本项目只负责确认、版本指针和 Codex 宿主桥接。

## 当前结论

- 与成熟平台正面竞争：不够资格，功能、社区、发布和生产证据差距巨大。
- 与零到两星直接同类竞争：核心差异化和安全证据已经有竞争力，但真实用户闭环、公开 CI、许可证识别、Release 和陌生人安装仍未全部通过。
- 是否值得继续：值得，但只能坚持窄定位。优先完成真实宿主重复验收和首个可复现 Release，再考虑真正 diff，不能先堆团队、云端和 AI 改写功能。

## 客观评价

本项目不是“功能最多”的，也没有资格用 stars 少来证明别人差。当前最可靠的优势是权限边界、失败口径和小依赖面；最严重的短板是没有公开用户和发布链证据。
