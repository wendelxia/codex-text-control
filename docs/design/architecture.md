# 架构说明

## 一句话目标

让 Codex 用户能修改一段上下文、保存不可变版本，并且只有在用户明确点击后，才把指定版本提交为当前对话的权威上下文。

真实用户是需要长期维护项目要求的 Codex 桌面用户。核心任务是“编辑 -> 保存 -> 确认提交 -> 后续对话采用 -> 重开可恢复”。当前替代方案是手工重发整段文字或直接改会话历史；前者容易丢版本，后者破坏审计和升级兼容。

当前明确不做通用提示词平台、多人协作、模型评测、云同步和逐行 diff。成功条件是用户可重复完成核心流程，草稿与权威版本不混淆，失败可理解并可恢复；失败条件是按钮卡死、模型能绕过用户写入、提交后对话不可见或重开丢失。

## 系统边界和数据流

```text
模型只读工具
  -> render_text_control_widget（打开编辑器）
  -> Widget 等待 Codex 宿主桥接完成
  -> 用户点击保存
  -> save_text_revision（仅应用可调用）
  -> revisions/<id>.json（不可变完整快照）
  -> 用户点击提交
  -> commit_authoritative_context（仅应用可调用）
  -> current.json（只保存当前版本编号和提交时间）
  -> Widget 向当前对话发送新的用户消息
  -> 后续模型读取并遵守权威上下文
```

## 模块职责

| 位置 | 输入 | 输出 | 职责和客观评价 |
|---|---|---|---|
| `mcp/context-storage.mjs` | 项目目录、正文、版本编号 | JSON 快照和当前指针 | 存储层简单、可恢复；当前没有并发锁和加密。 |
| `mcp/server.mjs` | MCP 工具请求 | 结构化结果和 Widget 数据 | 统一权限与输入上限；仍依赖 Codex 宿主正确执行应用权限。 |
| `mcp/widget-resource.mjs` | Widget HTML、宿主 App | 桥接对象和状态事件 | 负责握手与超时；双层超时会增加少量重复逻辑，但能隔离宿主不响应。 |
| `ui/editor.html` | 权威版本、历史、用户编辑 | 保存/提交请求、状态提示 | 单文件便于作为 MCP 资源注入；功能继续增长时应拆分，避免维护困难。 |
| `skills/codex-text-control/` | 用户自然语言意图 | 何时打开编辑器的模型规则 | 普通对话默认直通；规则只能约束模型，真正写权限仍由 MCP 元数据强制。 |

## 失败与恢复

- 桥接没连接：写按钮保持禁用，用户关闭后重开。
- 工具超时：按钮恢复并显示“结果未知”，用户先看历史再决定是否重试。
- 保存成功、消息回传失败：磁盘权威指针保留，界面分别报告两种结果；用户重开后可读取版本，再手工确认对话状态。
- 指针损坏或版本不存在：读取明确失败，不静默退回最新草稿，避免把未确认内容当权威。
- 插件回退：替换插件代码，不删除项目 `.codex-text-control/` 数据。

## 安全边界

正文、说明和大模型输出默认不可信。协议层和存储层都限制长度，界面只使用 `textContent`。Widget 内容安全策略不允许外部网络。保存和提交工具是 `app-only`，模型看不到写工具。项目目录目前没有沙箱限制，这是公开发布前必须继续评估的风险。

## ADR-001：完整快照加权威指针

采用“每个修订保存完整正文，`current.json` 只指向一个修订”的方式。原因是上下文通常不大，完整快照比补丁链更容易恢复、校验和人工检查。替代方案是逐行 diff 或数据库；它们节省部分空间，但增加重放、迁移和损坏恢复复杂度。当前选择用少量磁盘换低复杂度。

## ADR-002：用新用户消息更新对话

不修改 Codex 内部历史文件，而是在用户确认后发送一条新的用户消息。原因是公开插件接口支持消息追加，而私改内部数据库会破坏兼容性和审计。代价是旧消息气泡不会原地变化，但冲突时能明确看到哪个版本后来被确认。

## 客观评价

这套架构的窄边界是优势：没有模型、数据库和云服务，故障面小。它也决定了项目不应冒充 Langfuse 一类全功能平台；真正价值是 Codex 内的“用户确认成为权威上下文”闭环。
