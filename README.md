# Codex Text Control（Codex 文本控制）

这是一个本地 Codex 插件，用来编辑模型回复并把用户确认后的文本提交为新的权威上下文。

> 当前成熟度：**验证通过的本地候选版**。自动测试、MCP 探测、干净依赖安装和本机安全审计已通过；真实用户重复提交、线上 CI、公开 Release 和陌生人安装尚未全部验证，因此不能称为“可用”或“可发布”。证据见 [`docs/evidence/verification-2026-08-31.md`](docs/evidence/verification-2026-08-31.md)。

## 一句话理解

它像“带版本历史的上下文编辑器”：你可以删掉重复要求、补充验收条件、修正术语，然后点击提交。插件会保存文件，并向当前 Codex 对话追加一条明确的用户消息，因此后续回答会以修订版为准。

## 默认是普通聊天

插件默认不会干预普通对话。你没有明确说“修改、编辑、删减、整理、提交”时，Codex 就按原来的方式正常回答，不会自动弹出编辑器，也不会偷偷保存或改变上下文。

只有你明确提出修改要求时，才会打开编辑流程。例如：

```text
编辑刚才的回复，删掉重复内容
```

下面这些仍然是普通聊天，不会触发编辑器：

```text
继续
好的
解释一下
```

## 获取和验证源码

当前还没有公开仓库 URL 和 Release（发行版），所以这里不能给出一条假装可用的 `git clone` 命令。拿到源码目录后，可以在 Windows、macOS 或 Linux 上执行：

```powershell
npm ci --ignore-scripts
npm run quality
npm run verify:candidate
```

要求 Node.js（JavaScript 运行时）22 或更高版本。`npm ci --ignore-scripts` 会严格按锁文件安装，并拒绝依赖安装脚本；当前依赖树不需要这类脚本。`quality` 会运行行为测试、语法检查和 MCP 闭环探测；`verify:candidate` 还会使用 npm 官方注册表检查生产依赖漏洞、包签名和来源证明。这个命令名强调它只能验证候选版，不能替代真实用户闭环、线上 CI 和公开 Release。

本机开发环境通过个人 marketplace（个人插件市场）安装，命令是：

```powershell
codex plugin add codex-text-control@personal
```

这条命令只适用于已经配置本地 `personal` marketplace 的开发者，不是陌生用户安装方法。首次公开发布前必须提供真实仓库地址、发布标签、完整安装流程和回退流程。

## 使用

可以直接对 Codex 说：

```text
打开上下文编辑器并修改当前回复
```

或者：

```text
把刚才的要求整理一下，删掉重复内容，但先不要提交
```

编辑器里的三个动作含义：

- **保存修订版本**：保存一个新快照，不影响当前权威版本。
- **提交权威上下文**：保存并设为当前权威版本，再发回当前对话。
- **恢复当前权威版本**：放弃编辑器里的临时修改，载入已提交版本。

## 项目文件

插件会在当前项目创建：

```text
.codex-text-control/
  current.json        当前权威版本的指针
  revisions/          每个修订版本的完整 JSON 快照
```

为什么要保存完整快照？因为完整快照比“只保存改了哪几个字”的补丁更容易恢复，也更适合检查上下文有没有被误删。代价是文件会稍微多一些，但通常远小于代码项目本身。

这个插件把不同性质的东西分开放，避免以后找不到“哪一份才是真的”：

## 为什么现在的按钮不会永久卡住

Widget bridge（组件桥接）是编辑器与 Codex 宿主之间的通信通道。旧版在桥接尚未完成连接时就可能调用工具，而且等待没有上限；只要请求一直不返回，按钮就一直禁用。

`0.2.0` 做了三层约束：

1. 保存和提交工具明确声明 Widget 可以调用。
2. 每次工具调用必须先等待 `ui/initialize`（界面初始化）握手完成。
3. 桥接层和界面层都有 timeout（超时）保护；超过上限会显示明确错误并恢复按钮。

为什么要双层超时？桥接层保护所有调用者，界面层保护当前按钮。可以把等待时间写成：

`实际等待时间 = min(工具返回时间, 超时上限)`

`min` 表示“取较小值”。例如工具 2 秒返回、上限 30 秒，实际等待 2 秒；工具永远不返回，实际等待最多 30 秒，然后允许用户重试。

## 安全边界

- 版本编号、修改说明和正文都按纯文本处理，不把用户内容写进 `innerHTML`。`innerHTML`（直接写 HTML）会让 `<img onerror=...>` 之类的文本变成可执行页面内容，因此这里使用 `textContent`（纯文本内容）。
- 提交正文不能为空，后端和界面都会校验。
- 正文最多 100 万字符，修改说明最多 2000 字符；界面、MCP 输入结构和存储层三处使用同一上限，避免绕过前端造成无界内存或磁盘消耗。
- 相同正文已经有修订版本时，保存和提交会复用已有版本，避免每点一次就制造一个重复文件。
- 保存和提交属于写操作，只允许 Widget 调用；模型仍可打开编辑器和读取权威版本，但不能绕过用户界面直接提交。
- 权威版本提交成功后，即使向当前对话回传消息失败，界面也会分别报告“提交已成功”和“消息未发回”，不会把已发生的提交说成失败。
- 超时只能证明“在上限内没收到响应”，不能证明服务端没有执行，所以界面会显示“结果未知”，要求先核对版本历史。

## 验证命令

```powershell
npm.cmd run quality
npm.cmd run verify:candidate
```

`quality` 会依次运行 19 项自动测试、JavaScript 语法检查和 MCP 闭环探测。依赖审计使用 npm 官方注册表，是因为部分镜像没有实现安全审计接口；“接口不支持”不能算“没有漏洞”。

## 权威上下文的数学例子

可以把当前权威版本理解为一个指针函数：

`current = pointer(revisionId)`

例如版本集合是 `{R1, R2, R3}`，当前指针是 `R2`，那么 `current = R2`。再次提交 `R2` 后仍然是 `R2`，不会变成 `{R2, R2}`，这就是幂等（idempotent，重复执行结果稳定）。

## 客观限制

- 插件不会修改已经显示的旧消息气泡。
- 提交动作会追加一条新的用户消息，这是 Codex 插件当前更稳定、可追踪的上下文更新方式。
- 如果 Widget bridge（组件桥接）不可用，保存和提交按钮会保持禁用并显示连接错误；它不会假装已经保存。
- 自动测试使用当前安装的 MCP SDK（MCP 软件开发工具包）和浏览器运行时。其他 Codex 版本仍需要重新做一次真实宿主验收，汇报时不能把本机结果外推成“所有版本都可用”。
- 当前没有真正的逐行 diff（差异对比）界面；历史列表只能载入完整快照。
- 当前没有公开安全联系人、多操作系统真实宿主结果或线上 CI 记录，这些仍是首个公开 Release 的阻塞项。
