# Codex Text Control（Codex 文本控制）

## 默认行为：普通对话直通

这是最重要的规则：**用户没有明确要求修改文字时，按普通 Codex 对话处理。** 不打开编辑器、不调用 `render_text_control_widget`、不保存修订版本，也不追加“权威上下文”消息。

只有出现明确的修改意图才进入编辑流程，例如“编辑刚才的回复”“删掉重复内容”“改一下这段”“整理后提交”“以后按这版执行”。像“继续”“好的”“解释一下”“正常聊聊”这类普通对话，不属于修改意图，应保持原来的通话体验。

如果一句话既没有修改动词，也没有“以此为准/提交/整理”这类确认词，就按普通对话处理，不主动打断用户。

## 这个技能解决什么问题

模型已经输出的文字不能直接当作“用户确认过的事实”。本技能把它分成三个状态：

1. **草稿 draft（草稿）**：正在编辑的内容，可以随时改。
2. **修订 revision（修订版本）**：保存过的完整快照，旧版本不会被覆盖。
3. **权威上下文 authoritative context（权威上下文）**：用户明确点击提交后，后续工作应优先遵守的版本。

这不是篡改历史消息。它的实际做法是：保存文件，然后发送一条新的用户消息，明确声明“以这个版本为准”。这样模型可见上下文和磁盘记录是一致的。

## 使用流程

当用户说“编辑当前回复”“帮我删掉重复内容”“把这版作为最终要求”时：

1. 调用 `render_text_control_widget`（打开上下文编辑器）。如果能准确取得刚刚的回复，把它放入 `sourceText`；否则让用户在编辑器中粘贴。
2. 让用户在编辑器里修改正文和“本次修改说明”。不要把未经用户确认的内容直接提交为权威版本。
3. 用户点击“保存修订版本”时，只调用 `save_text_revision`，这一步不改变权威上下文。
4. 用户点击“提交权威上下文”时，调用 `commit_authoritative_context`。然后把返回的 `followUpMessage` 通过 widget bridge 发回当前对话。
5. 后续回答遵守最新权威版本；如果用户再次提交新版本，以新版本为准。

## 约束和边界

- 不要直接修改 Codex 内部会话数据库或 JSONL 历史文件。
- 不要把“保存修订”误称为“已生效”；只有提交后才是权威上下文。
- 读取项目状态时优先调用 `get_authoritative_context`，不要凭记忆猜测上一版要求。
- 版本文件位于用户项目的 `.codex-text-control/`，它属于项目数据，不会写入插件安装目录。
- 文本里可以包含 Markdown、代码和中文标点；存储层按 UTF-8 原样保存，不做破坏性格式化。

## 验收标准

- 修改后能看到版本编号，旧版本仍可载入。
- 重复提交同一版本不会生成额外版本，也不会重复改变内容。
- 提交后当前对话收到带版本号的“权威上下文已提交”用户消息。
- 关闭并重新打开项目后，仍能读取当前权威版本。

## 术语翻译和客观评价

- **Context（上下文）**：模型用来理解任务的背景、要求和决定。
- **Revision（修订版本）**：一次完整保存的文本快照，类似文档的“另存为版本”。
- **Authoritative（权威）**：用户已经确认，后续冲突时优先采用。
- **Idempotent（幂等）**：同一操作重复执行，结果不会不断叠加；例如重复提交同一个版本不会重复增加内容。

客观评价：这个方案稳定、可审计、容易恢复，但它不会把已经显示的旧气泡改成新文字；它是通过追加一条新的用户上下文来改变后续行为。这样牺牲了“视觉上的原地替换”，换来了历史可追溯和升级兼容性。
