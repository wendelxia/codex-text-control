# Codex Text Control（Codex 文本控制）

## 普通对话直通

除下述明确触发条件外，用户没有要求修改文字时按普通 Codex 对话处理。不打开画布、不保存版本。像“继续”“好的”“解释一下”“正常聊聊”这类普通对话保持原体验。用户明确要求不打开、只在聊天里回答时，优先服从该要求；不因模型自己附加了一句建议而触发。

当前文存在正在讨论的回复、文字、规则或上下文时，“我来改下”“我自己改一下”“让我改”“我改改”表示用户要亲自编辑，必须打开画布。没有指定对象时，目标是紧邻本轮请求之前的完整助手回复，原样传入 `sourceText`，不是磁盘里碰巧存在的旧上下文。用户明确指定更早的回复或某个表格时，使用其指向的原文。找不到可确定的正文时简短澄清，不能拿旧项目内容顶替。

不要只看“改”字触发；“我来改代码”“我改天再说”“我已经改完文件了”分别属于代码任务、时间安排和已完成操作。讨论插件故障、询问触发语的含义或引用一句“让我改”，都不是实际编辑请求。

## 打开上下文画布

每次调用任何 MCP 工具都必须显式传入 `projectDir`，值为当前工作区根目录。不得省略 `projectDir`；省略时旧版本会把插件安装目录误当成项目，新版本会直接拒绝。用户指定了其他项目路径时，使用用户指定的项目根目录。

用户说“打开上下文画布”“直接改上下文”“修改上下文里的表格”“删掉或增加上下文文字”时：

1. 先确定用户要编辑哪份内容。编辑聊天回复时直接使用该回复的完整原文，不润色、不重新生成，也不因已有权威版本改选目标。
2. 调用 `render_text_control_widget`，传入当前工作区根目录；编辑聊天回复必须同时传入匹配的 `sourceText`。只有用户明确要求打开已保存上下文或继续未保存草稿时，才先调用 `get_authoritative_context` 并在渲染时省略 `sourceText`，由后端恢复对应内容。不要只换标题而遗漏正文。用户仅说“打开上下文画布”时按打开保存内容处理。
3. 默认显示排版后的正文，点击正文进入原位编辑；段落、列表、表格和代码保持同一份连续内容。没有独立文本框、源码标签、常驻工具栏或重复的回复副本。
4. 用户修改时，Widget 先保留当前画布内草稿；输入停顿后把草稿写入项目 `.codex-text-control/drafts/`，不改变权威版本，也不把中文输入法中间态写入历史版本。
5. 只有编辑时显示“保存”和“取消”。用户点击“保存”后，Widget 调用仅应用可见的 `update_authoritative_context`，一次完成不可变修订并更新权威版本，再向对话回传简短版本通知，不重复全文。保存按钮就是本次确认，不再增加检查弹窗。模型不能代替用户调用写工具。

初次打开不生成正式版本；编辑停顿会自动保存可恢复草稿，但不会更新权威版本。新候选正文可直接点击“保存”接受，内容未变且已经确认时不重复保存。点击“取消”恢复进入本轮编辑前的正文并清理草稿；恢复的草稿取消后回到确认版本。切换对话会保留草稿，页面隐藏时尽力立即写入。输入法中间态不写入。若权威基线已变化，恢复草稿会明确提示并阻止静默覆盖。

## 画布更新后的必做动作

收到下面格式的实际保存通知时（引用示例、解释通知含义和工具排错不算保存通知）：

```text
【上下文画布已更新】
版本：rev-...
```

必须先调用 `get_authoritative_context`，显式传入当前工作区根目录，读取磁盘上的当前权威正文，再继续回答。默认返回最近一段；若 `truncated: true` 且当前任务需要前部内容，以 `fullContent: true` 按需读取完整确认版本，不得把截断结果当全文。不得凭聊天里较早的全文猜测，不得要求用户粘贴全文，也不得在回复里复述整份上下文。只需简短确认已采用哪个版本。确认版本优先于更早的同主题内容，不改变系统或开发者指令的优先级。

## 结论稿自动进入画布

当用户本轮要求整理成可直接采用或执行的完整结论稿时，即使没有明确说“编辑”，也调用 `render_text_control_widget`，传入当前工作区根目录，并把完整最终答复原样放入 `sourceText`。自动进入画布时，必须先完成整份最终稿，再调用工具；不得在草稿尚未完整时提前调用。以下情况触发：

- 把一段讨论、零散想法或多份信息整理成结论、决策、需求或共识。
- 按用户要求形成完整的推荐方案、执行计划、规则、优先级或验收标准。
- 将用户的意图重组为可直接继续使用的完整文本，而不只是回答一个问题。

判断用户要交付的内容，不以模型认为“这句话值得保存”为依据。不按字数或排版判断；表格或连续编号不能单独触发。单点问答、单句建议和普通解释优先按普通聊天处理，例如“哪个更简单，一句话说结论”或“给一句建议”都不自动打开。用户要求可亲自编辑时仍按明确编辑请求处理。

以下情况不自动打开画布：

- 本轮主要产物已经生成、修改或交付到代码、文件、文档或外部系统；最终回复只是交付说明，即使包含总结、表格或编号也不触发。
- 简短对话、单点问答、确认、解释、进度汇报、澄清问题或状态说明。
- 命令输出、日志、报错、代码块、工具返回、引用材料或用户输入。

只判断完整最终回复，工作过程中的进度消息不得触发。同一份最终稿最多调用一次 `render_text_control_widget`，不得重试生成第二个相同画布；工具成功返回后立即停止正文生成，不再在聊天中复述全文。若宿主要求最终消息，只给一句简短状态。不得用空画布探测当前上下文；探测只能调用 `get_authoritative_context`。正文第一次出现时就是可编辑版本，用户点击“保存”后才更新权威版本。

## 命名 AI 扩展点

扩展点仍使用唯一、不嵌套、独占一行的标记：

```text
【AI扩展点：发布门槛】
这里是允许 AI 补充的内容
【/AI扩展点】
```

用户要求“只补充扩展点‘发布门槛’”时：

1. 先调用 `get_authoritative_context`，传入当前工作区根目录，确认名称存在并理解附近固定要求。
2. 只生成扩展点内部的候选文字，不润色、压缩或重排扩展点外正文。
3. 调用 `render_text_control_widget`，传入当前工作区根目录、`extensionPoint` 和块内 `extensionText`，不传完整 `sourceText`。
4. Widget 只显示块内排版正文；用户点击“保存”后通过受限工具保存并更新，后端从基准权威版本重建全文。
5. `extensionText` 不能包含扩展点起止标记。权威版本变化、重名、嵌套、孤立或未闭合时必须拒绝。

## 约束

- 不修改 Codex 内部会话数据库或 JSONL 历史。
- 版本文件位于项目 `.codex-text-control/`，不是插件安装目录。
- Markdown 是磁盘权威格式；原位编辑是其排版视图。没有修改的顶层段落保留原始 Markdown，编辑过的段落转回 Markdown。
- 原始 HTML 只作为文字显示，不执行；粘贴只接收纯文本。图片显示为不联网的文字占位并保留引用。
- 旧的 `save_text_revision` 与 `commit_authoritative_context` 继续兼容，但新画布主流程不显示两步按钮。
- 相同正文复用已有修订；过期基准必须拒绝，不能覆盖并发修改。

## 验收

- 连续正文和 Markdown 表格原位编辑，可全选、复制、粘贴。只有编辑时出现保存、取消；Ctrl/⌘+Enter 保存，Escape 取消，输入法组合态不触发快捷键。
- 编辑停顿或页面隐藏时只保存草稿，点击保存后才创建正式版本。取消会等待在途草稿写入后清理，防止取消后草稿复活。
- 正文随内容自动增高，不设置固定高度或内部滚动区；边框仅向宿主请求关闭，宿主自己的标识不由插件控制。
- 完成保存期间锁定编辑控件；超时后恢复操作，本地内容不丢失。
- 超时、通知失败和并发冲突时，本地编辑内容仍保留且提示准确；过期草稿只能由用户显式载入，核对完整正文后再按当前基线提交。
- 历史版本仍由 `list_text_revisions` 查询，旧修订不被覆盖；扩展点外正文逐字不变。

## 客观评价

这是接近原生消息的组件体验，不能接管既有原生消息。没有全格式文档编辑器的插表、合并单元格和数学公式功能；图片只保留引用。宿主边框、加载标识和消息确认行为需在真实宿主验证。保存后的版本通知仍是新的简短用户消息。
